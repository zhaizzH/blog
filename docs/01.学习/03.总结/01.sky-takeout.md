# 苍穹外卖总结

> 本文档是对苍穹外卖项目技术实现的完整梳理，涵盖三层架构详解、参数传递机制、数据封装体系、中间件集成策略、认证安全实现及 Mapper XML 实战。适合已了解项目概览后深入阅读。

---

## 1. 项目总览

苍穹外卖是一套完整的线上外卖点餐系统，覆盖**用户端（微信小程序）** 与**商家管理端（Vue 管理后台）**，采用前后端分离架构，后端基于 SpringBoot + MyBatis 构建。

### 1.1 三大板块

| 板块 | 职责 | 技术选型 |
|------|------|----------|
| 业务功能模块 | 订单、支付、菜品、用户、购物车、数据统计 | Controller → Service → Mapper 三层 |
| 后端技术体系 | 请求处理、业务编排、数据访问 | SpringBoot + SpringMVC + MyBatis |
| 数据存储与部署 | 持久化、缓存、文件存储、网关 | MySQL + Redis + OSS + Nginx |

### 1.2 三套环境

| 环境 | 目的 | 部署要点 |
|------|------|----------|
| 开发环境 | 开发调试 | JDK + MySQL + Redis + Maven 本地运行，IDE 直接启动 |
| 测试环境 | QA 验证 | 单机/简易集群，配置贴近生产，导入模拟数据进行测试 |
| 生产环境 | 正式服务 | 多实例 + Nginx 负载均衡 + 数据库主从 + Redis 集群 + Docker 容器化 |

## 2. 三层架构深度解析

### 2.1 Controller 层 — 参数接收的三种方式

Controller 不处理业务逻辑，仅负责接收前端参数并调用 Service。前端传参方式决定了 Controller 的接收注解：

#### 方式一：路径参数（@PathVariable）

从 URL 路径中提取 ID 等标识。

```java
@DeleteMapping("/dish/{id}")
public Result delete(@PathVariable Long id) {
    orderService.delete(id);
}
```

**适用场景**：根据 ID 查询、删除、状态变更。

---

#### 方式二：查询参数（@RequestParam，可省略）

从 URL `?key=value` 中提取参数，SpringMVC 按名称自动匹配。

```java
@GetMapping("/employee/page")
public Result page(EmployeePageQueryDTO queryDTO) {
    // Spring 自动将 ?page=1&pageSize=10 封装到 queryDTO
}
```

**适用场景**：分页、筛选、列表查询。参数可见、长度受限。

---

#### 方式三：JSON 请求体（@RequestBody，最重要）

参数放在请求体中，以 JSON 格式传递。适用于登录、新增、修改等敏感或复杂数据提交。

```java
@PostMapping("/login")
public Result login(@RequestBody EmployeeLoginDTO dto) {
    // JSON: {"username":"admin","password":"123456"}
}
```

**为什么 POST/PUT 用 JSON 而非查询参数？**
- JSON 可以传递嵌套对象、数组等复杂结构
- 参数不暴露在 URL 中，安全性更高
- 没有长度限制

---

#### 参数接收速查表

| 场景 | 请求方式 | 参数位置 | 注解 | 示例 |
|------|----------|----------|------|------|
| 根据 ID 查询 | GET | URL 路径 | `@PathVariable` | `/dish/{id}` |
| 分页/条件查询 | GET | URL 问号后 | `@RequestParam` 或省略 | `/page?page=1` |
| 新增/修改/登录 | POST/PUT | 请求体 | `@RequestBody` | 传 JSON |
| 删除 | DELETE | URL 路径 | `@PathVariable` | `/dish/{id}` |

---

### 2.2 Service 层 — 业务核心

Service 层是项目的"大脑"，负责业务规则的编排与执行。

**职责清单：**
1. **接收** Controller 传入的 DTO
2. **校验** — 数据非空、状态合法、业务规则满足
3. **编排** — 按顺序调用 Mapper 完成多表操作
4. **事务** — 保证多步数据库操作的原子性
5. **转换** — DTO → Entity（入库）、Entity → VO（返回）
6. **调用第三方** — 微信支付、OSS 上传、WebSocket 推送

**为什么 Controller 不能直接写业务逻辑？**

| 理由 | 说明 |
|------|------|
| 职责单一 | Controller 只做"接收与响应"，不写判断逻辑 |
| 代码复用 | 多个 Controller 可调用同一 Service 方法 |
| 便于维护 | 业务变更只改 Service，不动 Controller |
| 事务管理 | `@Transactional` 在 Service 层生效 |

---

### 2.3 Mapper 层 — 数据访问

Mapper 只做一件事：与数据库打交道。

**技术实现：**
- 接口 + `@Mapper` 注解
- 简单 SQL → 注解（`@Select`、`@Insert`）
- 复杂 SQL → XML 映射文件

```java
@Mapper
public interface EmployeeMapper {
    // 注解 SQL — 适合简单查询
    @Select("select * from employee where username = #{username}")
    Employee getByUsername(String username);

    // 复杂逻辑写在 XML 中
    void insert(Employee employee);
}
```

## 3. 四层数据封装体系

苍穹外卖用了四层数据模型，每层有明确的职责边界：

| 步骤 | 环节 | 说明 |
|------|------|------|
| ① | 前端 → DTO | 前端 JSON 请求体经 `@RequestBody` 解析为 DTO |
| ② | Service: DTO → Entity | 数据转换、业务校验，封装为 Entity 持久化对象 |
| ③ | MyBatis: Entity ↔ MySQL | Mapper 层执行 CRUD，持久化至数据库 |
| ④ | Service: Entity → VO | 屏蔽敏感字段、多表组装，返回给前端展示 |
| ⑤ | Result 统一包裹 | Code + msg + data 标准化返回 |

### 3.1 Entity（实体类）

- 与数据库表一一对应，字段最全
- 包含敏感字段（密码、盐值）
- 仅在 Service/Mapper 内部使用，不返回前端

### 3.2 DTO（Data Transfer Object）

- **流向**：前端 → 后端
- **作用**：接收前端传来的参数
- **特点**：按接口需求裁剪字段、不与数据库表完全对应、配合 `@RequestBody` 使用

```java
@Data
public class EmployeeLoginDTO {
    private String username;
    private String password;
    // 只有登录需要的两个字段，不暴露数据库表结构
}
```

### 3.3 VO（View Object）

- **流向**：后端 → 前端
- **作用**：封装要返回给前端的数据
- **特点**：只返回前端需要的字段、屏蔽敏感信息、可组合多表数据

### 3.4 POJO 包命名规范速查

苍穹外卖项目中，POJO 类按用途分为三个包，命名规范清晰：

| 包名 | 全称 | 数据流向 | 职责 | 命名示例 |
|------|------|----------|------|----------|
| `dto` | Data Transfer Object | 前端 → 后端 | 封装前端请求参数 | `OrdersPaymentDTO` |
| `entity` | Entity | 仅后端内部 | 与数据库表一一对应，含全部字段 | `Orders`、`OrderDetail` |
| `vo` | View Object | 后端 → 前端 | 封装返回给前端的展示数据 | `OrderPaymentVO` |

**设计原则：**
- **dto** 不包含数据库表结构信息，仅含前端需要的输入字段
- **entity** 字段与数据库列完全一致，包含敏感字段（密码等），**严禁**直接返回前端
- **vo** 可跨表组合字段，屏蔽敏感信息，只暴露前端展示所需

> 三个包之间的转换在 Service 层完成，常用 `BeanUtils.copyProperties()` 进行属性拷贝。

### 3.5 Result（统一返回结果）

```java
@Data
public class Result<T> {
    private Integer code;    // 200 成功，其他失败
    private String msg;      // 提示信息
    private T data;          // 泛型数据
    private boolean success; // 是否成功
}
```

**设计收益**：前端只需一套解析逻辑处理所有接口。

## 4. Mapper XML 实战指南

苍穹外卖中 80% 的复杂 SQL 写在 XML 映射文件中，以下是高频标签的实战示例。建议先回顾第 3 节的数据封装体系，理解 Entity 与数据库表的对应关系后再阅读本节。

### 4.1 动态条件查询（`<where>` + `<if>`）

**业务场景**：员工分页查询，支持按姓名模糊搜索、按状态筛选。

```xml
<select id="pageQuery" resultType="com.sky.entity.Employee">
    select * from employee
    <where>
        <if test="name != null and name != ''">
            and name like concat('%', #{name}, '%')
        </if>
        <if test="status != null">
            and status = #{status}
        </if>
    </where>
    order by create_time desc
</select>
```

**`<where>` 的作用**：自动处理多条件时的 `AND` 前缀，避免写成 `WHERE AND name like...`。

### 4.2 动态更新（`<set>` + `<if>`）

**业务场景**：只更新前端传了的字段，没传的不更新。

```xml
<update id="update">
    update employee
    <set>
        <if test="name != null">name = #{name},</if>
        <if test="phone != null">phone = #{phone},</if>
        <if test="status != null">status = #{status},</if>
        <if test="password != null">password = #{password},</if>
    </set>
    where id = #{id}
</update>
```

**`<set>` 的作用**：自动删除多余的末尾逗号，避免 SQL 语法错误。

### 4.3 批量操作（`<foreach>`）

```xml
<!-- 批量删除菜品 -->
<delete id="deleteByIds">
    delete from dish where id in
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</delete>

<!-- 批量插入订单明细 -->
<insert id="insertBatch">
    insert into order_detail(name, image, order_id, number, amount) values
    <foreach collection="details" item="d" separator=",">
        (#{d.name}, #{d.image}, #{d.orderId}, #{d.number}, #{d.amount})
    </foreach>
</insert>
```

### 4.4 一对多嵌套查询（`<resultMap>` + `<collection>`）

**业务场景**：查询订单时同时查出所有订单明细。

```xml
<resultMap id="OrderWithDetailsMap" type="com.sky.vo.OrderVO">
    <id column="order_id" property="id"/>
    <result column="order_number" property="orderNumber"/>
    <result column="amount" property="amount"/>
    <result column="status" property="status"/>
    <collection property="orderDetails" ofType="com.sky.entity.OrderDetail">
        <id column="detail_id" property="id"/>
        <result column="name" property="name"/>
        <result column="number" property="number"/>
        <result column="amount" property="amount"/>
    </collection>
</resultMap>

<select id="getOrderWithDetails" resultMap="OrderWithDetailsMap">
    select o.id as order_id,
           o.order_number,
           o.amount,
           o.status,
           od.id as detail_id,
           od.name,
           od.number,
           od.amount as detail_amount
    from orders o
    left join order_detail od on o.id = od.order_id
    where o.id = #{id}
</select>
```

### 4.5 XML 标签速查

| 标签 | 用途 | 典型场景 |
|------|------|----------|
| `<where>` | 智能拼接 WHERE 条件 | 多条件模糊查询 |
| `<set>` | 智能拼接 SET 子句 | 动态更新 |
| `<if>` | 条件判断 | 所有动态 SQL |
| `<foreach>` | 集合遍历 | 批量删除、批量插入 |
| `<resultMap>` | 自定义结果映射 | 多表联查、字段名不一致 |
| `<collection>` | 一对多嵌套 | 订单+明细、菜品+口味 |
| `<sql>` + `<include>` | SQL 片段复用 | 公共查询列 |

### 4.6 执行 SQL 后返回自增主键

**业务场景**：插入订单后立即获取订单 ID，用于后续插入订单明细。

```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
    insert into orders (number, amount, status, user_id)
    values (#{number}, #{amount}, #{status}, #{userId})
</insert>
```

**参数说明：**
- `useGeneratedKeys="true"` — 告诉 MyBatis 使用数据库自增主键
- `keyProperty="id"` — 将生成的主键值赋值给传入实体对象的 `id` 属性

插入完成后，直接通过实体对象的 getter 获取：

```java
ordersMapper.insert(order);
Long orderId = order.getId(); // 此时 id 已被回填
```

**为什么需要这个机制？** 提交订单时，先插入 `orders` 表获取订单 ID，再以此 ID 批量插入 `order_detail` 明细表。没有主键回填，就需要额外一次查询。

### 4.7 MyBatis 中使用比较运算符

在 MyBatis XML 中写 `<` 或 `>` 会与 XML 标签语法冲突，有两种解决方案。

#### 方式一：XML 转义字符

| 字符名称 | SQL 符号 | 转义字符 |
|----------|----------|----------|
| 大于号 | `>` | `&gt;` |
| 小于号 | `<` | `&lt;` |
| 不等于 | `<>` | `&lt;&gt;` |
| 大于等于 | `>=` | `&gt;=` |
| 小于等于 | `<=` | `&lt;=` |
| 与 | `&` | `&amp;` |
| 单引号 | `'` | `&apos;` |
| 双引号 | `"` | `&quot;` |

**示例**：查询超时未支付订单

```xml
<select id="getTimeoutOrders" resultType="com.sky.entity.Orders">
    select * from orders
    where status = #{status}
      and create_time &lt;= #{deadline}
</select>
```

#### 方式二：`<![CDATA[ ]]>` 包裹

被 `<![CDATA[ ]]>` 包裹的内容不会被 XML 解析器解析，可原生书写 SQL 符号。

| 字符名称 | SQL 符号 | CDATA 写法 |
|----------|----------|------------|
| 大于号 | `>` | `<![CDATA[ > ]]>` |
| 小于号 | `<` | `<![CDATA[ < ]]>` |
| 不等于 | `<>` | `<![CDATA[ <> ]]>` |
| 大于等于 | `>=` | `<![CDATA[ >= ]]>` |
| 小于等于 | `<=` | `<![CDATA[ <= ]]>` |

**示例**：查询超时未支付订单

```xml
<select id="getTimeoutOrders" resultType="com.sky.entity.Orders">
    select * from orders
    where status = #{status}
      and create_time <![CDATA[ <= ]]> #{deadline}
</select>
```

#### 两种方式对比

| 对比维度 | 转义字符 | CDATA |
|----------|----------|-------|
| 可读性 | 差（符号不直观，IDE 不高亮） | 好（保留原字符） |
| 书写效率 | 需记忆转义表 | 直接包裹即可 |
| 常见位置 | 简单 WHERE 条件 | 复杂 SQL 片段 |

**推荐**：优先使用 `<![CDATA[ ]]>`，可读性更强；在需要混合动态标签（如 `<if>`）时注意 CDATA 的开闭位置。

## 5. 中间件集成详解

### 5.1 Redis — 三大存储场景

| 场景 | Key 设计 | 数据结构 | 过期策略 |
|------|----------|----------|----------|
| 菜品缓存 | `dish_cache_{categoryId}` | String(JSON) | 手动清理（`@CacheEvict`） |
| 购物车 | `cart_{userId}` | String(JSON) | 下单后手动删除 |
| 验证码 | `sms_code_{phone}` | String | TTL 5 分钟自动过期 |

**缓存一致策略：** 新增/修改/删除菜品时，通过 `@CacheEvict(value = "dishCache", allEntries = true)` 清空该分类所有缓存，下次查询时回填。

```java
@Cacheable(value = "dishCache", key = "#categoryId")
public List<Dish> listByCategory(Long categoryId) {
    return dishMapper.selectByCategoryId(categoryId);
}

@CacheEvict(value = "dishCache", allEntries = true)
public void saveWithFlavor(DishDTO dto) {
    // 新增操作 — 清理缓存
}
```

### 5.2 WebSocket — 实时推送

**为什么用 WebSocket 而非轮询？**

| 对比维度 | HTTP 轮询 | WebSocket |
|----------|-----------|-----------|
| 实时性 | 取决于轮询间隔（秒级） | 实时（毫秒级） |
| 资源消耗 | 大量无效 HTTP 请求 | 单条长连接，按需推送 |
| 通信方向 | 仅客户端→服务端 | 全双工双向通信 |
| 适用场景 | 低频数据刷新 | 订单推送、消息通知 |

**业务场景流程：**

| 步骤 | 环节 | 说明 |
|------|------|------|
| ① | 用户支付 | 小程序支付成功 → 触发支付回调 |
| ② | 订单处理 | OrderService 更新订单状态为"待接单" |
| ③ | 服务端推送 | 调用 `WebSocketServer.sendToUser(商家ID, 消息)` |
| ④ | 长连接传输 | 推送内容: `{"type":"newOrder","orderId":xxx}` |
| ⑤ | 商家端接收 | 后台网页收到 → 语音播报 + 订单详情弹窗 |

**核心代码说明：**

```java
@Component
@ServerEndpoint("/ws/{userId}")
public class WebSocketServer {
    // 维护 userId → Session 的映射
    private static Map<Long, Session> sessionMap = new ConcurrentHashMap<>();

    @OnOpen
    public void onOpen(Session session, @PathParam("userId") Long userId) {
        sessionMap.put(userId, session);
    }

    @OnClose
    public void onClose(@PathParam("userId") Long userId) {
        sessionMap.remove(userId);
    }

    public static void sendToUser(Long userId, String message) {
        Session session = sessionMap.get(userId);
        if (session != null && session.isOpen()) {
            session.getBasicRemote().sendText(message);
        }
    }
}
```

### 5.3 阿里云 OSS — 文件存储

**为什么图片不存数据库？** 数据库不适合存大文件，会导致表膨胀、查询变慢。OSS 成本低、访问快、支持 CDN 加速。

**上传链路：**

| 步骤 | 环节 | 说明 |
|------|------|------|
| ① | 前端上传 | 选择图片文件，以 MultipartFile 提交至 `/upload` 接口 |
| ② | 后端处理 | Controller 调用 `AliOssUtil.upload(fileName, inputStream)` |
| ③ | OSS 存储 | 阿里云 OSS 存储文件，返回访问 URL |
| ④ | 入库 | URL 写入 MySQL dish.image 字段 |
| ⑤ | 前端展示 | 请求菜品时直接加载 OSS URL（可配置 CDN 加速） |

## 6. 通用增强机制

### 6.1 拦截器 — JWT 认证

拦截器属于 SpringMVC 的扩展组件，在请求进入 Controller 前后统一处理。

**苍穹外卖中的 JWT 认证拦截：**

```java
@Component
public class JwtTokenInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 1. 从请求头获取 token
        String token = request.getHeader("Authorization");
        // 2. 解析 token，获取 userId
        Claims claims = JwtUtil.parseToken(token);
        Long userId = Long.valueOf(claims.get("userId").toString());
        // 3. 存入 ThreadLocal
        BaseContext.setCurrentId(userId);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        BaseContext.remove(); // 必须清除，防止内存泄漏
    }
}
```

**为什么拦截器 + ThreadLocal 是标配？**

1. **无状态认证** — JWT 不依赖 Session，分布式部署任意扩展
2. **链路传参** — 同一个请求线程内，Controller / Service / Mapper 都能通过 `BaseContext.getCurrentId()` 获取当前用户
3. **解耦** — 每个接口不用额外增加 userId 参数

### 6.2 AOP 切面

AOP 用于抽取"横切逻辑"（日志、权限、性能监控），不侵入业务代码。

**核心术语对应关系：**

| 术语 | 含义 | 代码体现 |
|------|------|----------|
| 切面 (Aspect) | 横切逻辑的封装类 | `@Aspect` + `@Component` |
| 切点 (Pointcut) | 给哪些方法加 | `execution(* com.sky.service.*.*(..))` |
| 通知 (Advice) | 什么时候加 | `@Around` / `@Before` / `@After` |

**经典应用场景 — 接口耗时日志：**

```java
@Aspect
@Component
@Slf4j
public class TimeAspect {
    @Around("execution(* com.sky.controller.*.*(..))")
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed();
        long elapsed = System.currentTimeMillis() - start;
        log.info("{} 耗时 {}ms", pjp.getSignature().getName(), elapsed);
        return result;
    }
}
```

### 6.3 全局异常处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(PasswordErrorException.class)
    public Result handlePasswordError(PasswordErrorException ex) {
        return Result.error(ex.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result handleException(Exception ex) {
        log.error("未知异常：", ex);
        return Result.error("系统繁忙，请稍后重试");
    }
}
```

**设计原则**：不向客户端暴露异常堆栈，业务异常返回友好提示，系统异常统一兜底。

## 8. 事务应用场景

| 业务场景 | 涉及表 | 重要性 |
|----------|--------|--------|
| 提交订单 | orders + order_detail + shopping_cart + dish (库存) | ★★★★★ 缺一不可 |

        // 3. 清空购物车
        // 4. 扣减库存
        // 任一失败全部回滚

## 11. 疑问解答

### 11.1 为什么 Mapper 接口不需要实现类？

MyBatis 在启动时通过 `@Mapper` 扫描接口，利用 **JDK 动态代理** 生成代理对象注入 Spring 容器。调用接口方法时，代理对象根据方法名或注解找到对应的 SQL 并执行。这个设计免去了传统 DAO 层的实现类，让 SQL 和 Java 代码的绑定关系集中管理。

### 11.2 主键 ID 和业务 ID 为什么分开？

| 维度 | 主键 ID | 业务 ID（如订单号） |
|------|---------|---------------------|
| 唯一性 | 数据库强制、自增 | 自定义规则（时间戳+随机数） |
| 对外暴露 | 严禁 | 专门对外 |
| 可修改 | 严禁 | 可重新生成 |
| 用途 | 表关联、数据库内部 | 用户查看、客服查询、接口调用 |

**原因**：自增主键若暴露，竞争者可通过 ID 差值推算业务量。业务 ID 使用无规律序列，安全且灵活。

### 11.3 Spring 和 SpringMVC 是什么关系？

**Spring** 是通用框架，核心是 IoC 容器和 AOP，管理所有 Bean 的生命周期。**SpringMVC** 是 Spring 的 Web 模块，专门处理 HTTP 请求。两者是父子容器关系：Spring 父容器管理 Service/Mapper，SpringMVC 子容器管理 Controller/拦截器。SpringBoot 则是整合二者的脚手架，实现自动配置。

### 11.4 DTO / VO / Entity 的字段不一致怎么办？

这是正常的设计——它们各自服务不同的目的：
- **DTO** 的字段 = 前端需要传入的字段
- **Entity** 的字段 = 数据库表的字段
- **VO** 的字段 = 前端需要看到的字段

三者通过 Service 层的手动转换或工具类（BeanUtils.copyProperties）进行映射，互不耦合。
